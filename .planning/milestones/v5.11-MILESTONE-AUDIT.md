### Phase 144 override (accepted, informational)

The live >1024-host end-to-end run confirmed 201 acceptance, job completion (twice), and
batch-failure isolation — but reported 0 open ports, including on a `127.0.0.1` with 5 genuinely
open ports. Root-caused via raw `nmap -oX` XML: no `<ports>` block was written for the affected
host, while the identical isolated nmap command found all 5 in 0.02s. Attributed to nmap's
adaptive RTT/timing engine on a synthetic loopback-alias target list that is ~99.9% silent — a
condition real routed networks don't produce (dead hosts return RST/ICMP-unreachable, not
silence). DISC-01/DISC-02's actual mechanisms are unaffected. Override signed by the user.

### Note on finding 6 — the conclusion was right for the wrong reason

The Phase 143 `uat_gap` row justified STILL BLOCKED with *"origin/main's last push was 2026-06-18;
zero GitHub Actions runs exist after that commit."* That was false by the time it was written or
shortly after: `git ls-remote` shows `origin/main` at `83ba306`, identical to local HEAD, with
Python CI, Dashboard Quality and Python Staleness Gate all green on it.

The item is still blocked, but for a structural reason the original rationale missed entirely:
`release.yml`, which contains the `windows-package` job and its Authenticode signing step, fires
only on `push: tags: ['v*.*.*']`. The newest remote tag is **`v5.9`**. So no windows-latest release
build has run for the Phase 139-147 work regardless of push state, and none will until a release
tag is cut. UAT-143-03 therefore has **two independent gates** — the missing production signing
cert *and* the absent release tag — where the ledger previously recorded one. Both are now stated.

This is the failure mode a re-triage is meant to catch: a disposition that is *correct* but resting
on evidence that has since decayed will survive every future review unchallenged, because reviewers
check the verdict rather than re-deriving the reasoning.
