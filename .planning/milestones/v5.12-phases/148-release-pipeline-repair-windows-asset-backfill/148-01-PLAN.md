THE TWO GUARD EXPRESSIONS — use these literal strings, do not paraphrase:

  RELEASE_GUARD (gates real-release side effects):
      github.event_name == 'push' && startsWith(github.ref, 'refs/tags/')

  DRY_RUN_GUARD (exact logical complement, gates the dry-run artifact upload):
      ${{ !(github.event_name == 'push' && startsWith(github.ref, 'refs/tags/')) }}

Why the `github.event_name == 'push'` conjunct is load-bearing (do NOT drop it): a
`workflow_dispatch` run can target ANY ref, including a tag — `gh workflow run release.yml --ref
v5.11.0`, or the tag dropdown in the Actions UI. In that case `github.ref` is `refs/tags/v5.11.0`
while `github.event_name` is `workflow_dispatch`. A ref-shape-only guard therefore evaluates TRUE
on a manual run against a tag, and the "dry-run" would really publish to PyPI and really attach a
zip to a real GitHub Release — the exact outcome D-06 and Success Criterion 1 forbid, and the exact
provenance risk D-01..D-04 exist to avoid. The event-name conjunct is what makes the guard sound;
`push` only ever fires via this workflow's `on: push: tags: ['v*.*.*']` filter, so
`event_name == 'push'` alone already implies a tag ref — the `startsWith` conjunct is retained as
defense-in-depth in case a branch push trigger is ever added.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub event → workflow execution | A `workflow_dispatch` event (any user with write access, any ref) now reaches a workflow that previously only ran on a tag push |
| Workflow → PyPI (OIDC Trusted Publisher) | `publish` job mints an OIDC token and uploads a distribution |
| Workflow → GitHub Releases | `windows-package` job holds `contents: write` and can create/mutate Release objects |
| Workflow → third-party Actions | Every `uses:` executes third-party code inside a job holding `contents: write` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-148-01 | Elevation of Privilege | `publish` job reachable via `workflow_dispatch` | mitigate | Job-level `if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/')` gates the entire job. Because the guard tests the triggering EVENT and not merely the ref shape, no `workflow_dispatch` run mints the PyPI OIDC token or invokes `pypa/gh-action-pypi-publish` — including a dispatch deliberately targeting a tag ref, where `github.ref` is `refs/tags/…` but `github.event_name` is `workflow_dispatch` (D-06). Locked by `test_publish_job_gated_on_push_event_and_tag_ref`. |
| T-148-01b | Elevation of Privilege | Guard weakened to ref-shape-only by a future edit | mitigate | `test_no_guard_is_ref_shape_only` asserts that every `if` mentioning `startsWith(github.ref, 'refs/tags/')` also carries `github.event_name == 'push'`, so silently dropping the event conjunct — reintroducing the dispatch-against-a-tag publish path — turns the local suite red with an explanatory message. |
| T-148-02 | Tampering | `Attach zip to GitHub Release` reachable via `workflow_dispatch` | mitigate | Identical event+ref guard on the step. `softprops/action-gh-release` CREATES the Release when absent, so an event-blind guard would let a dispatch against any tag fabricate or overwrite a Release and its assets — precisely the provenance failure D-01..D-04 reject. With the event conjunct, no dispatch run of any kind creates or mutates a Release. Locked by `test_release_attach_step_gated_on_push_event_and_tag_ref` and `test_both_release_guards_are_identical`. |
| T-148-03 | Spoofing | Dry-run artifact mistaken for a released artifact | mitigate | Dry-run zip is uploaded under the distinct name `quirk-windows-dry-run` (never `quirk-windows-<version>.zip` as a Release asset), and the runbook states a dry-run has zero external side effects. Artifact carries no Sigstore attestation, unlike published dists. |
| T-148-04 | Tampering | Guards silently removed by a future edit | mitigate | `tests/test_release_workflow_dryrun_guards.py` asserts both guards, their byte-identity to each other, their polarity (`!` present/absent), the exact-complement form of the dry-run guard, and step ordering; it runs on every local `pytest` invocation. |
| T-148-SC | Tampering | Third-party Action supply chain | mitigate | No new action is introduced — the dry-run upload reuses the existing `actions/upload-artifact@ea165f8d…` pin (D-07). `test_all_uses_are_sha_pinned` enforces 40-hex-SHA pinning on every `uses:` in the file (WR-03). No `npm`/`pip`/`cargo` installs are added by this plan, so the package-legitimacy gate does not apply. |
| T-148-05 | Information Disclosure | Signing secrets in a dispatch-triggered run | accept | `Determine signing capability` reads `secrets.QUIRK_SIGNING_CERT_*`, which are currently unset (UAT-143-03 still blocked), and the existing `Clean up production signing artifacts` step runs `if: always()`. Dispatch changes who can trigger the read, but repo-write access is already required to trigger it, and no new secret exposure surface is created. |
| T-148-06 | Denial of Service | Dispatch-triggered runner consumption | accept | Only users with repo write access can dispatch; a wasted windows-latest runner minute is a cost, not a security event. |
</threat_model>
