<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local repo → origin/main | Pushing workflow changes makes new triggers live for every user with repo access |
| Operator CLI (`gh`) → GitHub Releases API | Creating a Release object mutates public release history |
| Dispatched workflow → PyPI / Releases | A dispatch run executes the same workflow that publishes on tags |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-148-16 | Elevation of Privilege | Dry-run dispatch reaching PyPI | mitigate | Task 2 asserts the `publish` job conclusion is literally `skipped` and that the PyPI version list is byte-identical before and after — a positive proof of the corrected D-06 event+ref guard, not an assumption. If `publish` is anything other than `skipped`, the task fails. The dispatch-against-a-tag variant is covered by static test rather than a live run (see the interfaces note), because a failed live experiment would itself cause the harm. |
| T-148-17 | Tampering | Dry-run mutating GitHub Releases | mitigate | Task 2 captures `gh release list` before and after and requires byte-identical output, and asserts the `Attach zip to GitHub Release` step is `skipped`. |
| T-148-18 | Spoofing | Fabricated release history | mitigate | Only the `v5.11.0` Release is created, bound to the pre-existing pushed tag via `--verify-tag`, with zero assets and `--latest=false`. No Release is created for `v5.9`/`v5.10.0` (explicitly prohibited in the action), so no tag gains an artifact or a status its pipeline never produced. |
| T-148-19 | Repudiation | Unverifiable "it works" claim | mitigate | `148-04-EVIDENCE.md` records run IDs, run URLs, per-job/per-step conclusions and the `SELF_TEST_SIGNING: OK` log line — third parties can re-open the exact runs. This is the D-08 requirement that inspection alone is insufficient. |
| T-148-20 | Tampering | Irreversible push to the default branch | mitigate | Task 1 is a `checkpoint:human-action` blocking gate requiring explicit approval after diff review, and asserts no release tag is pushed alongside. |
| T-148-21 | Denial of Service | Guard turned permanently red, then ignored | mitigate | Task 2 step 6 explicitly forbids baselining a genuinely-new flagged tag to force green, so alert fatigue is not manufactured by suppression. |
| T-148-SC | Tampering | Supply chain of dispatched workflow | mitigate | The dispatched workflows contain only SHA-pinned actions (enforced by the static tests in 148-01/148-02). This plan adds no `uses:` step and no `npm`/`pip`/`cargo` install, so the package-legitimacy gate does not apply. |
</threat_model>
