<objective>
Wire score-lift through the dashboard API: per-node `score_lift` on `RoadmapNode`, top-level
`projected_score` on `ScanLatestResponse`, and their TypeScript mirrors.

Purpose: LIFT-05 names `routes/scan.py` wiring explicitly, and Phase 202's storyline drawer consumes
this payload's per-item number joined by slug. The transport shape decided here is the contract the
next phase builds on.

Output: two additive Optional pydantic fields, their TS mirrors, the `_derive_roadmap` lift join, the
endpoint's projection call, and a serialization/degradation test.

Hard constraints:
- Additive-Optional only. `RoadmapNode.score_lift: Optional[float] = None`,
  `ScanLatestResponse.projected_score: Optional[float] = None`. TS mirrors are `number | null`, never
  undefined-only (Phase 199 convention, UI-SPEC locked).
- `projected_score` is a TOP-LEVEL sibling of `roadmap`, NOT a field of `ScoreData`. Putting it inside
  `ScoreData` would trip the firewall's real-score-surface assertion — by design.
- No new endpoint. `_derive_roadmap` has exactly one call site (scan.py:1756); keep it that way.
- Thread `profile=stored_profile` and NO `weights`, matching the endpoint's own
  `compute_readiness_score(evidence, profile=stored_profile)` at scan.py:1657. Do not normalize the
  CLI/dashboard calibration asymmetry in this phase.
- Lift failure must degrade to absence, copying the closure-state lookup's try/except +
  `logger.exception(... advisory-only, skipping)` posture — an advisory number must never break the page.
- Do not render anything in `.tsx` pages here; plan 201-06 owns `roadmap.tsx` / `print.tsx`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server -> dashboard client (`/api/scan/latest`) | New advisory numeric fields cross this boundary. Server-computed integers only; no operator input participates in their construction. |
| projected score -> real score surface | `projected_score` is deliberately placed OUTSIDE `ScoreData` so the firewall's surface inventory stays true. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-201-11 | Tampering | `projected_score` placed inside `ScoreData` (or any `score`-named block), making a simulated value indistinguishable from the real score | mitigate | Top-level sibling placement; `test_forward_projection_firewall.py`'s ScoreData field assertion re-run as an acceptance criterion |
| T-201-12 | Denial of service | A raising lift computation taking down `/api/scan/latest`, removing the whole roadmap from the operator's dashboard | mitigate | try/except -> `{}` / `None` with `logger.exception`, mirroring the closure-state lookup; two explicit degradation tests asserting HTTP 200 with a populated roadmap |
| T-201-13 | Information disclosure | A stale or zero lift rendered as if real after a computation failure | mitigate | Degradation yields `None`, never `0`; the `is None` assertion (not a falsy check) is an acceptance criterion |
| T-201-14 | Tampering | Lift numbers computed with a different profile than the surface's own current score, silently disagreeing with the displayed headline | mitigate | `profile=stored_profile`, no weights — the endpoint's own arguments, quoted in the SUMMARY; the asymmetry is documented, not normalized |
| T-201-15 | Elevation of privilege | A new unauthenticated endpoint exposing projection data | accept | No new endpoint; the existing `/api/scan/latest` auth posture is unchanged |
| T-201-SC | Tampering | npm/pip/cargo installs | accept | No packages installed |
