<objective>
Attach real lifts to roadmap items at the report callers and render them on the CLI markdown surface,
carrying both the per-item number and the aggregate projection into the shared `ExecContent` so the
HTML and DOCX renderers (plan 201-07) can consume them without recomputing.

Purpose: LIFT-05 requires the report surfaces and the dashboard to show the SAME numbers for the same
scan. That holds only if each surface computes lifts with the arguments it already uses for its own
headline score, and only if a single content model carries the values to all three renderers.

Output: two defaulted dataclass fields, a `build_exec_content` kwarg, lift computation at the
`writer.py` and `executive.py` seams, and the `(+N pts)` / projected-line rendering in CLI markdown.

Hard constraints:
- Do NOT add `score_lift` inside `build_phased_roadmap()`. `tests/test_intelligence_roadmap.py:52-56`
  asserts the items' exact 6-key set; attachment happens at the caller, on the returned dicts.
  `quirk/intelligence/roadmap.py` stays byte-unchanged.
- New dataclass fields are APPENDED LAST WITH DEFAULTS. Every existing `RoadmapItem` field is
  non-defaulted; inserting a field mid-list breaks every constructor.
- `build_exec_content`'s three existing call sites pass positionally — the new parameter must be an
  optional keyword with a default.
- The intelligence-JSON `"score"` block is an explicit hand-maintained allowlist. Do not add anything
  to it. Lifts riding along inside the serialized `"roadmap"` value are fine and labeled.
- HARDEN-01: scanner-derived text goes through `md_cell()`; the `(+N pts)` literal is built from a
  server-computed int and is appended OUTSIDE `md_cell`, exactly like the existing `dep_txt`.
- The advisory disclaimer is verbatim, character for character:
  `Advisory — this projection is a simulation and does not affect the readiness score.`
- This plan does not touch `report.html.j2` or `docx_renderer.py` (plan 201-07) or any `.tsx`.
</objective>
