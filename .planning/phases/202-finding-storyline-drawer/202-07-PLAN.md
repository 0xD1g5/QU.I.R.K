<objective>
Extend the existing a11y harness with an opened-drawer capture — ROADMAP success criterion 4.

Purpose: the "existing WCAG AA discipline" criterion 4 refers to is concrete and already wired
(`run-a11y.mjs`, `pinned-deps.test.ts`, `@axe-core/puppeteer` pinned at `4.11.3`). D-04 says extend
it, with no new tooling and no new runner. The hard part is not the axe call — it is that three
separate mechanisms in this harness would each let the capture pass while scanning the WRONG DOM:
an unmatched `/api/findings` request 404s and the drawer renders its error state; the hand-maintained
`HOOK_TARGETS` list does not auto-detect new hooks; and a new baseline slug that
`ACCEPTED-VIOLATIONS.md`'s generator cannot see becomes accepted violations nobody reviews. All three
are closed here.

Output: the fixture handler and its payload, the `HOOK_TARGETS` entry, the interaction step, the
freshness-generator extension, the regenerated baselines, and a regenerated `ACCEPTED-VIOLATIONS.md`.

Hard constraints:
- **Do NOT add a `tests/console-allowlist.json` entry.** The harness fails on ANY console output not
  matched by that file, which today holds exactly one entry. Radix's `DescriptionWarning` is unguarded
  by `NODE_ENV` in the installed `@radix-ui/react-dialog` ^1.1.15, so opening the drawer during the
  capture would emit it — 202-06 renders `SheetDescription` to fix it at the source. If the capture
  fails on that warning, the fix is in `findings.tsx`, not in the allowlist.
- **Do NOT add a `routes.json` ROUTE entry for the drawer** (F10a). `routes.json` entries are
  `{slug, path, contentMarker}` only — there is no interaction hook — so a new route entry renders
  `/findings` with the drawer closed and baselines the wrong DOM. Extending the EXISTING `findings`
  entry with an optional interaction key is the correct shape.
- **Do NOT change the pinned versions.** `@axe-core/puppeteer` stays exactly `4.11.3` and the CI
  Chrome pin stays exactly as declared; `pinned-deps.test.ts` guards both and must pass unchanged.
- **No tolerance band.** Baseline counts are exact integers (harness D-06). Do not introduce a
  fuzz/threshold comparison to make a flaky count pass.
- **A violation found by this capture is a finding, not a number to baseline away.** If the opened
  drawer produces a CRITICAL-impact violation, `buildBaselineEntries`' own refusal path should fire —
  do not route around it. Fix the component (a 202-06 follow-up edit is in scope for this plan if so)
  and say so in the SUMMARY.
- `.tsx`/`.ts` edits require `npm run lint && npm run test` from `src/dashboard/`. This plan changes
  only `vite.config.ts` (whose `a11yFixture` middleware is active solely under `VITE_A11Y_FIXTURE`)
  and files under `tests/a11y/`, so **no production source changes and no statics commit** — 202-06
  owns the statics. If you find yourself needing to edit `findings.tsx`, that is allowed (see above)
  but then you MUST rebuild and commit statics with it, and say so.
- Plain `git add` + `git commit`; never the gsd `commit --files` wrapper. Do NOT invoke any mutating
  GSD verb, and do not touch `.planning/STATE.md`.
</objective>
