<objective>
Make report branding + template settings reusable across engagements as named profiles.

Purpose: RPT-04. Consulting engagements repeat the same house style; re-entering six branding
fields per engagement config is the friction this removes. The load-bearing correctness property
is the precedence rule: a profile fills gaps, it never overrides what the operator wrote.

Output: `quirk/report_profiles.py`, `quirk/cli/report_cmd.py`, the `run_scan.py` wiring, and
`tests/test_report_profiles.py`.

Hard constraints:
- `yaml.safe_load` / `yaml.safe_dump` ONLY. `yaml.load` is an RCE surface and is banned repo-wide.
- Route the profiles directory through ONE function honoring a `QUIRK_PROFILES_DIR` env override,
  mirroring the env-wins idiom in `get_vertical()` (config.py:856-876). Tests redirect via
  `monkeypatch.setenv` — do NOT monkeypatch `Path.home` (fragile on Windows CI), and do not write
  into the developer's real `~/.quirk` during tests.
- The profile NAME is a path component: validate it against a bare-identifier charset before it
  ever touches a path. Use the `CONFIG-004` code registered in plan 200-02 — do NOT add a new
  error code here (that would re-trip the `docs/error-codes.md` byte-match gate in a second plan).
- Do NOT extend `quirk/engine/profiles.py::apply_profile` — scan profiles are a different concept.
  Copy its `_set_if_unset` / `_user_set_fields` idiom into the new module.
- Do NOT touch `quirk/config.py` (plan 200-02 owns it, and the merge belongs in the new module),
  `quirk/reports/*` (plans 200-03/200-04 own those in this wave), or `quirk/errors.py`.
- `--config` is required for `profile save` — the save command reads the current config's settings.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| profile name (CLI arg or config value) → filesystem path | A name becomes a path component; `../evil` is a traversal vector even though the field is not declared as a path. |
| `~/.quirk/report_profiles/*.yaml` → config object | A YAML document from outside the engagement config tree is deserialized and its values are written onto the live cfg, including path-shaped values. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-200-15 | Tampering | Path traversal via a profile NAME (`report.profile`, `--report-profile`, `profile save <name>`) | mitigate | `validate_profile_name` enforces `[A-Za-z0-9_-]{1,64}` and runs BEFORE any path construction; coded `CONFIG-004` error; rejection legs assert no file is created outside the profiles dir |
| T-200-16 | Elevation of Privilege | Arbitrary object construction via unsafe YAML in a profile file | mitigate | `yaml.safe_load` exclusively; a dedicated test asserts a `!!python/object/apply` payload raises rather than executes |
| T-200-17 | Information disclosure | A profile file smuggling a traversal `template_dir`/`logo_path` past the config-load guard | mitigate | `apply_report_profile` routes every profile-supplied path value through `validate_report_path_field` (`CONFIG-003`); dedicated test leg |
| T-200-18 | Tampering | A profile silently overwriting an operator's explicit engagement-config value | mitigate | Merge gates on `ReportCfg._user_set_fields` flattened keys; the precedence test asserts both halves |
| T-200-19 | Denial of Service | Profile save clobbering an existing house style without notice | accept | Overwrite is the documented behaviour; the CLI reports it explicitly on stdout rather than failing |
| T-200-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; PyYAML 6.0.2 already present |
