# Domain/connector ratio denominators are approximate, not correct (999.113 D3)

**Filed as required by `.planning/decisions/999.113-denominator-semantics.md` D3**, which
explicitly forbids letting this be "quietly treated as solved." Do not close this todo by pointing
back at 999.113 -- 999.113 fixed the certificate and endpoint families and moved this family off
the worst defect (the probe count), but it did NOT give these ratios a correct denominator.

## The gap

Per D1's family table, three families now have honest, population-matched denominators:

- Certificate ratios (expired/expiring/self-signed) -> `certificate_observations.certs_observed`
- Endpoint ratios (plaintext HTTP, HTTP-on-TLS, legacy TLS, unknown services, mTLS) ->
  `assessable_endpoint_count`
- Findings ratio (high-impact) -> non-INFO finding count (`finding_severity_counts`, D1(d))

The fourth family -- domain/connector ratios -- does NOT:

- **DAR** (`dar_db_plaintext_ratio`, `dar_db_weak_ssl_ratio`, `dar_storage_unencrypted_ratio`,
  `dar_storage_aws_managed_ratio`, `dar_k8s_unencrypted_ratio`, `dar_k8s_inaccessible_ratio`,
  `dar_vault_weak_ratio`)
- **Motion** (`motion_email_plaintext_ratio`, `motion_email_weak_cipher_ratio`,
  `motion_broker_plaintext_ratio`, `motion_broker_weak_tls_ratio`,
  `motion_broker_weak_cipher_ratio`)
- **Agility connector signals** (`agility_weak_jwt_alg_ratio`, `agility_openapi_plaintext_ratio`,
  `agility_codesign_weak_algo_ratio`, `agility_fuzz_crypto_posture_ratio`)
- **Identity connector signals** (`identity_kerberos_weak_etype_ratio`,
  `identity_saml_weak_signing_ratio`, `identity_dnssec_weak_algo_ratio`, and the six
  `identity_smime_*`/`identity_adcs_*` count-weighted impacts)

all divide by `assessable_endpoint_count` (999.113 D3), which is the TLS/HTTP/SSH endpoint
population -- not the population these ratios actually describe. A database-plaintext ratio's
honest denominator is "how many databases were observed," not "how many TLS endpoints were
observed." Those per-connector-type observed-counts do not currently exist anywhere in
`evidence` (`quirk/intelligence/evidence.py`).

## Why this is still an improvement, not a no-op

Before 999.113, ALL 34 non-`agility_high_impact_ratio` sites (including this family) divided by
`totals.endpoints` -- the probe count including ADVISORY/CLOSED rows. Moving this family to
`assessable_endpoint_count` removes the "deep scan measures worse than shallow scan on identical
infrastructure" defect for it, same as it does for the certificate/endpoint families. It does NOT
give it a denominator whose numerator and denominator are drawn from the same population (D1's
core principle) -- a scan with 3 real databases and 1 plaintext one, alongside 50 clean TLS
endpoints, still divides 1 by ~50ish rather than by 3.

## What a real fix needs

1. **A per-connector-type "observed" counter in `evidence.py`.** E.g.
   `dar_db_observed_count`, `dar_storage_observed_count`, `dar_k8s_observed_count`,
   `dar_vault_observed_count`, `motion_email_observed_count`, `motion_broker_observed_count`,
   `identity_kerberos_observed_count`, etc. -- mirroring how `certs_observed` already works for
   the certificate family. This likely means widening whatever code path currently increments
   `protocol_counts[...]` (POSTGRESQL, MYSQL, RDS, S3, AZURE_BLOB, KUBERNETES, VAULT,
   SMTP-STARTTLS/SMTPS/..., KAFKA-*/AMQP-*/REDIS-*, KERBEROS, SAML, DNSSEC, SMIME, ADCS) to also
   track a distinct "observed regardless of weakness" tally per connector TYPE (not per protocol
   literal -- e.g. all of SMTP-STARTTLS/SMTPS/IMAPS/... collapse into one "email servers
   observed" count for `motion_email_*`'s denominator).
2. **Re-run this decision's acceptance-criteria protocol** (measure on the recorded multihost
   estate + a healthy fixture, check for new false floors) once the new denominators exist --
   D4's clamp-interaction warning applies here too, arguably more so, since some of these
   per-connector-type counts could be very small (e.g. 1 Vault instance), making any single
   weakness register as 100% of the population.
3. **Do not conflate this with 999.113's scope.** 999.113's acceptance criteria are already
   satisfied by the certificate/endpoint/findings-family fixes; this todo is deliberately scoped
   narrower and lower priority, per the decision doc's own instruction not to let D3 block 999.113
   from shipping.

## Feasibility & Effort

- **Feasibility: LIKELY** -- the mechanism (a parallel "observed" counter next to each existing
  weakness counter) is a known, already-precedented pattern (`certs_observed` exists for exactly
  this reason for the certificate family).
- **Effort: M** -- touches `quirk/intelligence/evidence.py`'s counting logic for ~15 distinct
  connector types across 4 categories (DAR, motion, agility-connectors, identity-connectors),
  plus `scoring.py`'s denominator wiring, plus golden-fixture regeneration, plus a second
  acceptance-criteria pass per D4.
- **Spike needed: no** -- the shape is clear from the certificate-family precedent; the volume of
  call sites is the main cost, not the design.
