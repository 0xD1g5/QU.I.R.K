# v5.18 "Migration Execution" — Sizing / Feasibility Investigation

**Date:** 2026-09-01
**Question source:** `.planning/HORIZON.md:263-270` (Candidate A)
**Type:** sizing/feasibility. Not a design proposal.
**Method:** source reading with file:line citation for every structural claim, plus live
data checks against `quirk-output/quirk.db` (10,069 rows), `output/quirk.db`, and two
consecutive real `output/findings-*.json` runs.

---

## Verdict (short)

**The 3x framing is wrong, and it is wrong in a way that matters.**

The two readings are *not* two sizes of the same feature. They are two different features
that share a name. Reading 2 (ticketing deepening) is genuinely small — **1 phase, ~4-5
plans** — because the ticketing layer already does a fingerprint-keyed read against the
tracker and simply throws the answer away. Reading 1 (QUIRK-native remediation tracking) is
**4-6 phases, ~18-26 plans**, not because tracking is hard, but because **QUIRK has no
persisted finding and no cross-scan finding identity**, and the one mechanism that looks
like it provides that identity is empirically dead.

So the ratio is closer to **4-5x than 3x** — and, more importantly, **Reading 2 does not
buy you a cheap version of Reading 1.** Reading 2 outsources item identity to Jira/ServiceNow
entirely. It produces zero infrastructure that Reading 1 would reuse. Picking it as "the cheap
option" and later wanting Reading 1 means paying Reading 1 in full, on top.

**There is a third, genuinely-cheap option the HORIZON question does not name** (see §7):
close the loop against the *roadmap items*, which already have a stable closed-set key,
rather than against findings, which do not. ~2 phases.

## 1. What the Phase 101–105 ticketing surface actually is today

### The abstraction

`TicketingChannel` is an ABC at `quirk/ticketing/base.py:32-59` with exactly three abstract
methods (`base.py:46-59`):

- `find_by_fingerprint(fp) -> Optional[str]`
- `create_issue_from_finding(finding, fp, evidence) -> str`
- `add_rediscovery_comment(issue_key, fp) -> None`

The base class owns fingerprint, evidence build, dedup orchestration, and the audit row
(`base.py:40-41`). Two concrete backends:

- `JiraChannel` — `quirk/ticketing/jira.py:26`, `destination = "jira"` (`jira.py:40`)
- `ServiceNowChannel` — `quirk/ticketing/servicenow.py:35`, `destination = "servicenow"`
  (`servicenow.py:49`)

### The SHA256 idempotent dedup

`TicketingChannel.compute_fingerprint` — `base.py:65-78`:

```
raw = f"{host}:{port}::{title}"
return hashlib.sha256(raw.encode("utf-8")).hexdigest()
```

Marked "NEVER override in subclasses" (`base.py:72`). Stored as a **Jira label**
(`jira.py:124`) and as ServiceNow **`correlation_id`** (`servicenow.py:134`). Looked up via
JQL `labels = "<fp>"` (`jira.py:97`) and `sysparm_query=correlation_id=<fp>`
(`servicenow.py:90-93`).

### Is the flow write-only?

**No — but the read is thrown away.** This is the single most important structural fact for
Reading 2.

`dispatch_finding` (`base.py:104-151`) already performs a **read against the live tracker**
every run: `existing_key = self.find_by_fingerprint(fp)` at `base.py:124`. Both backends
implement a real HTTP/JQL query (`jira.py:97-101`; `servicenow.py:89-113`).

Three things are discarded:

1. `find_by_fingerprint` returns only an opaque key/sys_id string — it explicitly does **not**
   return the issue object (`base.py:14-15`), so no status field ever crosses the boundary.
   Jira's search is narrowed to `maxResults=1` and only `.key` is read (`jira.py:98-100`);
   ServiceNow explicitly requests `sysparm_fields=sys_id` (`servicenow.py:92`) — the field
   projection actively excludes `state`/`incident_state`.
2. `create_issue_from_finding` returns the new key, and **`base.py:128` calls it without
   assigning the return value.** The freshly-minted ticket key is discarded at the call site.
3. `IntegrationDelivery` has **no column for the external ticket key** — `quirk/models.py:284-292`
   is exactly `id, scan_id, finding_hash, destination, status, attempted_at, error_summary`.
   `status` here means *delivery* status (`"ok" | "failed"`, `models.py:290`), never tracker status.

So the QUIRK-side record of "we filed a ticket for fingerprint X" exists
(`finding_hash`, `models.py:288`), but the record of "and it is ticket SEC-42" does not.

### The delivery/audit table

`integration_deliveries` — created idempotently by `_ensure_integration_deliveries_table`
(`quirk/db.py:459-467`), called from `init_db` at `quirk/db.py:537`. Shared by Phase 101
notify (`quirk/notify/dispatcher.py:241,262,281,377,396`), Phase 103 SIEM
(`quirk/siem/dispatcher.py:98`), Phase 104/105 ticketing (`base.py:139`), sensor ingest
(`quirk/dashboard/api/routes/sensor.py:250,267,355,557`) and sensor auth 401s
(`quirk/dashboard/api/middleware/sensor_auth.py:102`).

Note `scan_id` is indexed (`models.py:287`); **`finding_hash` is not** (`models.py:288`)
— any status-history query keyed on fingerprint would want that index.

### Entry point and surface

CLI only: `quirk ticket create` (`quirk/cli/ticket_cmd.py:42`, action choices `["create"]`
at `ticket_cmd.py:70-72`). Input is the newest `findings-*.json` on disk
(`ticket_cmd.py:29-34`). Dispatch loop: `ticket_cmd.py:186-188`.

**There is no dashboard ticketing route.** `ls quirk/dashboard/api/routes/` yields
`config, hardware_drift, health, jobs, merge, pdf, qramm, scan, schedules, sensor, trends` —
no ticket route, and `grep -rn "ticket" quirk/dashboard/api/routes/*.py` returns nothing.

**No delivery rows exist in either local DB** (`select count(*) from integration_deliveries`
→ `[]` in both `quirk-output/quirk.db` and `output/quirk.db`). The path has never been
exercised on this machine.

### What reading status back would actually require

Minimal honest list:

1. `find_by_fingerprint` widens its return to a small status struct, or a sibling
   `fetch_status(fp)` is added. Jira: drop `maxResults=1`-plus-`.key` and read
   `issue.fields.status.name` (`jira.py:98-100`). ServiceNow: add `state`/`incident_state`
   to `sysparm_fields` (`servicenow.py:92`) and parse it (`servicenow.py:108-109`).
2. A status→QUIRK-vocabulary mapping. This is config, not code: Jira workflow status names
   and ServiceNow `incident_state` codes are per-instance. There is no existing config
   surface for it — `quirk/ticketing/config.py` (174 lines) has none.
3. Somewhere to put the answer. Either two nullable columns on `integration_deliveries`
   (`external_key`, `tracker_status`) plus an index on `finding_hash`, or a new small table.
4. A read command — `quirk ticket sync` / `status` — since `action` is currently a
   closed choice list (`ticket_cmd.py:70-72`).
5. A surface to render it. Nothing in the dashboard or reports consumes ticket data today.

Everything above is additive against a working, SSRF-hardened, credential-scrubbing,
failure-isolated transport. **That is why Reading 2 is cheap.**

## 2. Cross-scan identity — the load-bearing question

### Answer: three incompatible identity schemes exist, and none of them identifies a finding across scans in a way remediation tracking can use.

#### Scheme A — hardware devices: `(host, port)`, with an explicit confidence grade

The most mature identity machinery in the codebase, and the only one designed for the job.

- `reconcile_device_history(session, host, port)` — `quirk/scanner/hardware_drift.py:510-518`,
  window from `recent_successful_hardware_rows(session, host, port, limit=m)`
  (`hardware_drift.py:548`; helper at `quirk/models_util.py:69`).
- `persist_and_reconcile` iterates `{(d.host, d.port) for d in devices}`
  (`hardware_drift.py:420-421`).
- N-of-M confirmation gate, fail-closed: `_confirmed_value` (`hardware_drift.py:62-83`),
  `DEFAULT_N = 2`, `DEFAULT_M = 3` (`hardware_drift.py:42-43`).
- `HardwareDevice.match_confidence` (`quirk/models.py:550`) is explicitly documented as
  **cross-scan IDENTITY-match confidence** and "deliberately distinct from `confidence`
  (probe-RESULT confidence). The two are never conflated." (`models.py:490-493`).
  Upgraded `low`→`high` only when an SSH host-key SHA256 fingerprint is available
  (`quirk/scanner/hardware_scanner.py:415-421`); baseline is `low`
  (`hardware_scanner.py:368`).

This scheme knows that `(host, port)` is a weak key and grades itself accordingly. It is
also **advisory-only by machine-enforced invariant** — `tests/test_cve_score_guard.py`
guards `hw_cve`, `hardware_drift`, `hardware_eol`, and `hardware_forecast` against ever
touching `SCORE_WEIGHTS`.

**It covers hardware devices only.** It says nothing about TLS, SSH, API, identity, DAR,
email, or broker findings.

#### Scheme B — trend engine: `(host, port, protocol, severity)` over `crypto_endpoints`

`quirk/intelligence/trends.py:225-247` computes `new_keys = current_keys - previous_keys`
and `resolved_keys = previous_keys - current_keys`, keyed on
`(ep.host, ep.port, ep.protocol, ep.severity)` (`trends.py:264-274`).

Two disqualifying properties:

**(a) Severity is in the key, deliberately.** `trends.py:206-208`: "severity included
intentionally so a HIGH→MEDIUM transition surfaces as 1 HIGH resolved + 1 MEDIUM new
(D-03)." That is the exact opposite of remediation tracking — partial remediation reads as
one item closed and one unrelated item opened.

**(b) `CryptoEndpoint.severity` is never populated for non-cloud endpoints.**
`grep` for assignments finds exactly seven, all in three cloud connectors:
`quirk/scanner/aws_connector.py:130,185,216,322`, `quirk/scanner/azure_connector.py:273`,
`quirk/scanner/k8s_connector.py:170,256`. **No TLS, SSH, API, identity, DAR, email, broker,
or hardware scanner sets it.** The key-set builders filter `ep.severity is not None`
(`trends.py:266,272`), so those endpoints are silently dropped.

**Verified live, not inferred:**

```
quirk-output/quirk.db: 10,069 crypto_endpoints rows, 0 with non-NULL severity
output/quirk.db:           30 crypto_endpoints rows, 0 with non-NULL severity
```

The existing new/resolved finding delta — the only cross-scan "movement" machinery in the
product — returns **0 new / 0 resolved for every scan on this machine**, and would for any
engagement not using the AWS/Azure/K8s connectors. This is a live defect adjacent to (not
identical with) the v5.17 lesson "an ORM column that is always NULL is not implemented"
(RETROSPECTIVE.md:1273, Top Lesson 7).

Note also that `trends.py` operates on `crypto_endpoints` rows, **not** on the
`findings-*.json` findings. An "endpoint" carries one severity; a scan of that endpoint can
emit several findings. Endpoint-level and finding-level are different granularities.

#### Scheme C — ticketing fingerprint: `SHA256(host:port::title)`

`base.py:65-78`. This is the closest thing to a finding-level cross-scan key that exists.

**Empirical stability check** — two consecutive real scans, `output/findings-20260831-203734.json`
vs `output/findings-20260901-203454.json`, 12 findings each:

```
fingerprints unique within a scan: 12/12 (no collisions)
stable across the two scans:       11
new:  1  →  127.0.0.1:8000 "HTTP on TLS-designated port"
gone: 1  →  127.0.0.1:8000 "Informational protocol observation"
```

So it works, mostly. But it has three structural weaknesses:

1. **Title is interpolated in 22 places.** `grep -rn 'title=f"' quirk/` → 22 hits:
   10 in `quirk/engine/findings_evaluator.py` (lines 166, 181, 203, 219, 237, 254, 266,
   1026, 1045, 1080), 12 in `quirk/dashboard/api/routes/scan.py` (146, 200, 307, 350, 377,
   412, 459, 620, 666, 686, 702, 725). The interpolated values include package versions
   (`findings_evaluator.py:181` — `({name}@{version})`), certificate subjects
   (`findings_evaluator.py:1026`), and **days-to-expiry**
   (`scan.py:200` — `f"Certificate expiring in {days_to_expiry} day(s)"`).

   `f"Certificate expiring in {days_to_expiry} day(s)"` produces a **new fingerprint every
   single day**. `f"...crypto library ({name}@{version})"` produces a new fingerprint
   **exactly when someone partially remediates by upgrading**. This is the "records that
   decay" failure mode: the key mutates under precisely the conditions remediation tracking
   is meant to observe.

   The compliance layer already knows about this and works around it —
   `TITLE_PREFIX_ALIASES` (`quirk/compliance/__init__.py:105-122`) maps 7 interpolated
   title prefixes to canonical keys, consumed by `_normalize_for_compliance`
   (`quirk/engine/findings_evaluator.py:42-47`). **That normalizer is not applied to
   the ticketing fingerprint.**

2. **`check_id` exists but is empty.** `_build_finding` accepts and emits `check_id`
   (`findings_evaluator.py:80, 115, 139`), but it is populated in only 13 places, all
   code-signing (`findings_evaluator.py:1038, 1055, 1066-1092`). Live check:
   **0 of 12 findings in the latest real scan carry a non-empty `check_id`.**
   The obvious stable key is present in the schema and unpopulated.

3. **Fingerprint provenance is a stale comment.** `base.py:69-71` states
   "findings-*.json has NO 'protocol' or 'category' keys (verified against real output)."
   Actual keys in a current findings file are
   `['check_id','compliance','description','host','port','quantum_risk','recommendation','severity','title']`
   — `check_id` and `compliance` both exist. The comment's conclusion (no `protocol`,
   no `category`) still holds; its "so title is the only available proxy" reasoning does not.

#### Direct answer to the question

**Can a finding be identified as "the same item" across two scans today?**

- Hardware devices: **yes**, by `(host, port)`, with self-graded confidence.
  `hardware_drift.py:510-548`.
- Cloud-connector endpoints: **technically yes**, by `(host, port, protocol, severity)` —
  but severity-in-key makes it wrong for remediation, and 0/10,069 rows are populated.
- Everything else — TLS, SSH, API, identity, DAR, email, broker, i.e. the bulk of the
  product: **no**. The only candidate key is `SHA256(host:port::title)`, it is computed
  transiently inside `dispatch_finding` and persisted only as an opaque
  `IntegrationDelivery.finding_hash` (`models.py:288`, unindexed) when the operator has
  ticketing configured and runs `quirk ticket create` by hand.

**There is no findings table.** `grep "class Finding" quirk/` returns only two Pydantic
response models (`quirk/dashboard/api/schemas.py:53, 433`). Findings are recomputed
from `crypto_endpoints` on every read, and the two recomputations do not agree with each
other — `quirk/engine/findings_evaluator.py` produces the JSON/report findings, while
`quirk/dashboard/api/routes/scan.py:106 (_derive_findings)`, `:325
(_derive_identity_findings)`, `:474 (_derive_motion_findings)`, `:556 (_derive_dar_findings)`,
`:779 (_derive_hardware_findings)` independently re-derive them for the UI, with their
own separate f-string titles.

## 3. What the remediation roadmap currently is

### Generation

Not `quirk/reports/executive.py` — that only renders. The generator is
**`quirk/intelligence/roadmap.py::build_phased_roadmap`** (`roadmap.py:99`, module is 468
lines, `ROADMAP_VERSION = "1.0.0"` at `roadmap.py:5`).

Consumed by:
- `quirk/dashboard/api/routes/scan.py:1090-1127` (`_derive_roadmap`), called at `scan.py:1535`
- `quirk/reports/executive.py:343-367` (NOW/NEXT/LATER section rendering)
- `quirk/reports/content_model.py:563-591` (`_enrich_roadmap_item`) and `:593-605`
  (`_sort_roadmap_items`)
- `src/dashboard/src/pages/roadmap.tsx:36` (`RoadmapPage`)

### Derived fresh, from aggregate counts

`build_phased_roadmap(evidence, scoring)` takes only two mappings and reads **aggregate
scalars**: `totals.endpoints`, `protocol_counts.UNKNOWN`, `plaintext_http_count`,
`cert_observations.expired_count/expiring_count/self_signed_count`,
`finding_severity_counts`, `scan_error.rate`, `tls_enum_coverage_ratio`,
`cert_key_type_counts.RSA/ECDSA` (`roadmap.py:140-155`).

Each roadmap item is a **hard-coded theme emitted behind a threshold**:

| Condition | Emitted title | Line |
|---|---|---|
| `plaintext_http_count + http_on_tls_count > 0` | Remove plaintext HTTP exposure | `roadmap.py:160-175` |
| `high_impact > 0` | Triage high-impact findings | `roadmap.py:177-192` |
| `expired_count > 0` | Replace expired certificates | `roadmap.py:194-206` |
| `scan_error_rate >= 0.2` | Stabilize scan reliability | `roadmap.py:208-223` |
| `unknown_count > 0` | Classify unknown open services | `roadmap.py:225-240` |
| `expiring_count > 0` | Renew near-expiry certificates | `roadmap.py:242-257` |
| `self_signed_count > 0` | Migrate self-signed certificates to managed PKI | `roadmap.py:259-271` |
| `legacy_tls_count > 0` | Disable legacy TLS versions | `roadmap.py:273-286` |
| `tls_enum_cov < 0.85` | Increase TLS enumeration coverage | `roadmap.py:288-303` |
| `rsa_count > 0 and ecdsa_count == 0` | Plan ECDSA adoption | `roadmap.py:305-320` |
| `mtls_present > 0` | Standardize mTLS lifecycle operations | `roadmap.py:322-336` |

Plus 3 deterministic baseline fillers to reach `min_items` (`roadmap.py:339-374`), a
governance-item special case (`roadmap.py:380-400`), and a 3-item empty-evidence fallback
(`roadmap.py:419-455`). Output truncated to `max_items` (default 12, `roadmap.py:105`).

**Total closed set: 17 possible titles.** No item references a host, a port, or a finding.

### Is any of it persisted?

**No.** `build_phased_roadmap` is a pure function over two dicts, called fresh on every
report render and every `GET /api/scans/...` response (`scan.py:1535`). There is no
roadmap table, no roadmap row, no `roadmap_id`.

### Addressable or positional?

**Both, oddly — and this is the most useful discovery in this section.**

- Internally, items **are keyed by title**: `_add_candidate` uses `items[title]` as the
  dict key with a documented merge rule (`roadmap.py:54-97`, "Merge a candidate into the
  items dict by title (D-06 / WR-08 Phase 73)"). Titles come from a closed 17-element set
  and are **fully stable across scans** — they contain no interpolated values.
- Externally, the emitted item dict has no `id` field (`roadmap.py:412-421`); it carries
  `phase, title, why, owner_placeholder, dependencies, timeframe`. `why` contains
  interpolated counts (`roadmap.py:167-170`), so `why` churns; `title` does not.
- The dashboard **synthesizes** a node id: `f"{phase_key}-{title[:20].replace(' ','-').lower()}"`
  (`scan.py:1110`). That id **changes if the item moves NOW→NEXT** — so the only
  externally-visible identifier is unstable in exactly the case that matters (an item
  de-prioritizing as remediation lands).
- Ordering is positional and recomputed: `_sort_roadmap_items` sorts by bucket then
  `-priority_score` (`content_model.py:593-605`), where `priority_score` comes from
  substring-matching the title against `EFFORT_IMPACT_MAP` (`content_model.py:563-591`).

**Bottom line: the roadmap's `title` is the only genuinely stable, closed-set, non-decaying
identifier anywhere in the product.** It is not currently exposed as one.

## 4. Data model delta

### Existing migration machinery (this is cheap, and the project knows it)

Two mature idempotent patterns:

- **New table:** an `_ensure_<name>_table(engine)` calling
  `Base.metadata.create_all(engine, checkfirst=True)`, wired into `init_db`. Precedents:
  `quirk/db.py:459` (integration_deliveries, Phase 101), `:474` (merge_runs, Phase 110),
  `:484` (hardware_drift_events, Phase 155), `:494` (vendor_pqc_trend_events, Phase 160).
  Call sites `quirk/db.py:537-541`.
- **New nullable columns:** a tuple appended to `_ADDITIVE_MIGRATIONS`, applied by the
  generic `_ensure_columns` helper (`quirk/db.py:213+`, consolidated in Phase 77 D-21).
  Precedents at `quirk/db.py:150-211` — Phase 133 SNMP, 139 SNMPv3, 140 bridge evidence,
  141 OT/ICS, 154 identity, 159 check-in, 146 scan-job progress.

### Reading 2 — ticketing deepening

| Change | Detail |
|---|---|
| `integration_deliveries.external_key` | `VARCHAR(64)` nullable — the discarded `base.py:128` return value |
| `integration_deliveries.tracker_status` | `VARCHAR(64)` nullable — mapped tracker state |
| `integration_deliveries.status_checked_at` | `DATETIME` nullable |
| Index on `finding_hash` | `models.py:288` currently unindexed; status lookup is by fingerprint |

**Four additive columns, one index, zero new tables.** This fits `_ADDITIVE_MIGRATIONS`
exactly and is a single plan. **"No new table" is genuinely achievable for Reading 2.**

Caveat: `integration_deliveries` is a **per-attempt append-only audit log** shared by six
subsystems (notify, SIEM, Jira, ServiceNow, sensor ingest, sensor auth). Overloading it into
a mutable current-state record for ticket status is a semantic mismatch — a status refresh
would either mutate an audit row (violating its append-only contract) or append a new row per
poll (unbounded growth with no retention policy; the only retention machinery in the codebase
is `purge_stale_hardware_history`, `hardware_drift.py:284-354`, and it is hardware-scoped).
An honest Reading 2 probably wants a separate small `ticket_status` table and should say so
rather than claim a zero-table win.

### Reading 1 — QUIRK-native

Reading 1 needs a **persisted finding with a stable identity**, which does not exist. Minimum:

| Change | Why |
|---|---|
| New table `finding_items` (or `remediation_items`) | No findings table exists — `grep "class Finding"` → only Pydantic schemas at `schemas.py:53,433` |
| Stable finding key column | Cannot be `SHA256(host:port::title)` — 22 interpolated titles decay it (`quirk/engine/findings_evaluator.py:181` etc.) |
| Populate `check_id` across all finding emitters | Currently 13 sites, code-signing only (`findings_evaluator.py:1038-1092`); 0/12 populated in live output |
| Lifecycle state column + transition history | Same shape as `hardware_drift_events` (`models.py:422-434`) |
| First-seen / last-seen / resolved-at | Not derivable from `crypto_endpoints` (`scan_run_id` is NULL on all 10,069 rows in `quirk-output/quirk.db`) |
| Retention/purge policy | New; no generic precedent |
| Backfill decision | Every additive migration to date is explicitly "never backfilled" (`db.py:191-193`, `db.py:197-203`) |

**One new table minimum, realistically two, plus a cross-cutting change to every finding
emitter.** The "no new table, no schema change" outcome recent milestones have valued is
**not achievable for Reading 1, and claiming otherwise would be dishonest.** The right
comparison is Phase 155, which added exactly one table (`hardware_drift_events`) plus
`persist_and_reconcile` and took a 17-plan milestone (v5.13) to land the surrounding
diffing layer.

## 5. The honest 3x claim

### Reading 2 — ticketing deepening: **1 phase, 4-5 plans**

| Plan | Work |
|---|---|
| 1 | Additive migration (`external_key`, `tracker_status`, `status_checked_at`, index) or the small `ticket_status` table |
| 2 | Widen the `TicketingChannel` contract with `fetch_status`; capture the discarded `base.py:128` return |
| 3 | Jira + ServiceNow status read + per-instance status→vocabulary config mapping |
| 4 | `quirk ticket sync` subcommand (`ticket_cmd.py:70-72` choice list) + surfacing |
| 5 | Docs + Obsidian sync + UAT-SERIES (mandatory per CLAUDE.md) |

**Drivers:** the transport, SSRF hardening, credential scrubbing, failure isolation,
audit-row pattern, dedup, and — critically — the tracker read itself all already exist
(`base.py:124`). This is genuinely additive.

**Risk that would inflate it:** status vocabulary mapping is per-customer configuration,
not code. If the milestone tries to auto-detect Jira workflow states or ServiceNow
`incident_state` codes, add a phase. Scope it as config-with-sane-defaults.

### Reading 1 — QUIRK-native: **4-6 phases, 18-26 plans**

| Phase | Work |
|---|---|
| A | Finding identity: a non-decaying stable key. Either populate `check_id` at all ~40 `_build_finding` sites, or apply `_normalize_for_compliance` (`findings_evaluator.py:42`) to a fingerprint. Includes the 22 interpolated titles. |
| B | Persisted finding items + migration + first-seen/last-seen/resolved-at + retention |
| C | Reconciliation: the Phase 155 `persist_and_reconcile` shape, generalized off hardware. Needs an N-of-M or equivalent confirmation gate — a finding must not read "resolved" because one scan timed out (the `current_error_hosts` exclusion at `trends.py:255-262` is the existing precedent for this hazard) |
| D | Roadmap item ↔ finding item linkage. Roadmap items are aggregate themes over counts (`roadmap.py:140-155`), not per-host items; there is no join today |
| E | Surfacing: reports (`executive.py:343-367`, `content_model.py`), dashboard (`roadmap.tsx`), CBOM, PDF/DOCX/HTML parity |
| F | Fix or replace the trend engine's dead severity key (`trends.py:264-274` + the 0/10,069 severity population) — otherwise the product ships two contradictory "resolved" concepts |

**Assumptions driving the estimate:**

- **Dominant:** whether Phase A can reuse `TITLE_PREFIX_ALIASES` normalization
  (`compliance/__init__.py:105-122`) rather than populating `check_id` across every emitter.
  Reuse ≈ 4 phases; full `check_id` population ≈ 6, and it touches
  `findings_evaluator.py` plus five independent `_derive_*_findings` functions in
  `dashboard/api/routes/scan.py` that must not diverge.
- Whether Phase F is in scope. Leaving the trend engine's broken delta in place while
  shipping a second, correct one is the "two contradictory answers" failure the project has
  repeatedly punished.
- Whether backfill is attempted. Every prior additive migration says "never backfilled"
  (`db.py:191-193`). Holding that line saves a phase and makes the first post-upgrade scan
  the baseline.
- v5.13 is the closest calibration point: 3 phases / 17 plans for "a scheduling/diffing/
  reporting layer over existing data, zero new deps" (RETROSPECTIVE.md:1246). Reading 1 is
  that, **plus** creating the data it diffs over.

### The ratio

**~4-5x, not 3x.** And the framing is wrong in kind, not just magnitude: these are not
two sizes of one feature. **Reading 2 produces no reusable infrastructure for Reading 1** —
it deliberately delegates item identity to the customer's tracker, which is the entire
problem Reading 1 has to solve. Choosing Reading 2 as "the cheap version" and later wanting
Reading 1 costs Reading 1 in full, on top.

**Are the readings cleanly separable?** Mostly, with one important exception: they share
`SHA256(host:port::title)` as the only existing finding-level key, and **both are damaged by
its 22 interpolated titles**. Reading 2 already silently suffers this today —
`f"Certificate expiring in {days_to_expiry} day(s)"` (`scan.py:200`) files a fresh Jira
ticket every day the scan runs. Fixing fingerprint stability is a prerequisite for either
reading and should be scoped as a shared Wave-0 phase regardless of which is chosen.

## 6. Traps specific to this codebase

**Trap 1 — Chokepoint or nothing.** RETROSPECTIVE.md:1292 (Top Lesson 18): "A
milestone-spanning shared chokepoint pays for itself when 3+ phases in the same milestone
need the same persistence path — design it for named future callers." `persist_and_reconcile`
(`hardware_drift.py:356`) was extracted in Phase 158 and absorbed 159 and 160 with zero
duplicated logic (RETROSPECTIVE.md:799-803). Reading 1 has **three** obvious call sites from
day one (CLI scan, dashboard-initiated scan, sensor merge ingest). The corresponding
anti-precedent is `_build_finding` (RETROSPECTIVE.md:284): "all new finding types should go
through `_build_finding()`; no direct dict construction" — and today
`dashboard/api/routes/scan.py` bypasses it entirely with five independent `_derive_*_findings`
functions. **If Reading 1 persists findings written by only one of those paths, the dashboard
and the reports will disagree about what is resolved.**

**Trap 2 — Advisory-only is machine-enforced, and remediation state is squarely inside its
blast radius.** `tests/test_cve_score_guard.py` asserts no `SCORE_WEIGHTS` key contains
"cve", and was extended by name in Phases 142, 155, and 157 to cover `hw_cve`,
`hardware_drift`, `hardware_eol`, `hardware_forecast`. The question Reading 1 must answer
explicitly at CONTEXT time: **does an item marked "remediated in Jira" change the readiness
score?** If yes, an unverified client assertion moves the consulting deliverable's headline
number — precisely the "false assurance in a consulting deliverable" risk theme the v5.10
research flagged as needing same-phase mitigation (HORIZON.md:300). If no, say so and add
the guard test in the same phase.

**Trap 3 — Records that decay.** RETROSPECTIVE.md:1290 (Lesson 16): "a correct conclusion
resting on decayed facts is invisible to every subsequent review." Three decay vectors here,
all verified:
  - the ticket fingerprint mutates on version bump and daily on expiry countdown
    (`findings_evaluator.py:181`, `scan.py:200`);
  - `purge_stale_hardware_history` hard-deletes history rows opportunistically per scan
    (`hardware_drift.py:284-354`, default 180 days) — any remediation history built on
    hardware rows inherits that purge;
  - a stale-comment example already exists in the ticketing layer itself: `base.py:69-71`
    asserts findings have no `category`/`protocol` key "verified against real output", while
    the live file's key set is
    `['check_id','compliance','description','host','port','quantum_risk','recommendation','severity','title']`.

**Trap 4 — Enumeration vs derivation.** RETROSPECTIVE.md:1083 and 1096: "Enumeration loses
entries; derivation does not" — the milestone's most-repeated failure, established three
times in a single phase (Phase 170, TRACE-05). The roadmap generator is a **hand-enumerated
list of 11 hard-coded titles** (`roadmap.py:160-336`). Any Reading-1 mapping from roadmap
items to findings will be a second hand-enumerated list, and it will silently omit entries
the same way. If a roadmap↔finding join is in scope, derive it from a shared constant
(`check_id`, or the `EFFORT_IMPACT_MAP`/`REMEDIATION_CATALOG` keys at
`content_model.py:261`), never from a parallel list.

**Trap 5 — Never inherit a count, and never inherit a closed conclusion.**
RETROSPECTIVE.md:1293 (Lesson 19, "four for four have failed re-measurement") and 1290/
Lesson 20 ("a closed root cause is a hypothesis until something independent confirms it" —
v5.17's most valuable finding came from re-running a closed investigation). **This document
is itself an instance:** the HORIZON "3x" is an inherited count and it does not survive
re-measurement. The severity finding (0 of 10,069 rows) is the same shape as
`TRIAGE-176-03` — a subsystem that has been silently degraded since it shipped, with green
tests, because nothing asserted the column was ever non-NULL. RETROSPECTIVE Top Lesson 7
already names this class: "an ORM column that is always NULL is not implemented."

**Trap 6 — Mandatory per-phase overhead.** `CLAUDE.md` requires per-phase doc updates
(report-interpretation, operators-guide, configuration for new config options), Obsidian
vault sync to `20_Dev-Work/QUIRK/Guides/`, `docs/UAT-SERIES.md` updates, and a phase note.
Both readings add a CLI command and a report surface, so both trip the "New CLI command"
and "New report section" rows of the Per-Phase Documentation Checklist. Budget one plan per
phase for this; it is not optional and it is not free.

## 7. The option the question does not name

The HORIZON framing presents a binary. There is a third option that is smaller than either
and is the only one that builds on a **non-decaying** key that already exists.

**Track completion against roadmap items, not findings.**

Roadmap item `title` is drawn from a **closed 17-element set**, contains no interpolated
values, is already used as the internal merge key (`roadmap.py:54-97`, `items[title]`), and
is stable across scans by construction. Nothing else in the product has those properties.

A minimal loop-closure would: assign each roadmap item a stable slug derived from `title`
(replacing the phase-dependent `scan.py:1110` synthesis, which breaks on NOW→NEXT movement);
persist per-item status + owner + target date in one small table; and render
"3 of 12 roadmap items closed since baseline" in the executive report and on
`roadmap.tsx`. It needs no finding identity, no fingerprint repair, no `check_id` campaign,
and no change to any scanner.

**Estimated 2 phases / ~8 plans.** It delivers the consulting-facing narrative HORIZON
actually describes — "showing movement against the roadmap rather than only against the
score" (HORIZON.md:266) — at roughly Reading 2's cost, without outsourcing the product's
core artifact to the client's ticketing system. It is also a strict prerequisite-free
stepping stone: if Reading 1 is later wanted, the roadmap-item table is the natural parent
for finding items.

This should be put in front of the PM at shaping time as a named third option, not folded
into either reading.
