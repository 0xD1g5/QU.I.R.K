**Dimension:** DOMAIN (ecosystem, not code)

**Mode:** Ecosystem
**Overall confidence:** MEDIUM-HIGH (regulatory dates and VEX/CycloneDX facts are HIGH — verified against

**Question v5.18 must answer:** closing the loop — tracking remediation items to completion across

---

## 0. The one structural fact that shapes everything

QUIRK's remediation roadmap today is **not a list of trackable items**. `quirk/intelligence/roadmap.py`
`build_phased_roadmap()` is a pure function over *aggregate evidence counters* that emits
template-titled, class-level candidates ("Remove plaintext HTTP exposure", "Triage high-impact
findings", "Replace expired certificates"), keyed by `title`, merged by
`(_PHASE_ORDER[phase], _priority, title)`, and **never persisted**. There is no per-asset identity,
no ID, no state, no history.

Meanwhile QUIRK *already has* three things that a tracking model needs:

| Existing asset | Location | What it gives v5.18 |
|---|---|---|
| Stable finding fingerprint `SHA256(f"{host}:{port}::{title}")` | `quirk/ticketing/base.py` `compute_fingerprint` | A per-finding identity already used for Jira/ServiceNow dedup |
| Session-delta engine with match key `(host, port, protocol, severity)` | `quirk/intelligence/trends.py` `compute_trend_report` | New/resolved computation across two sessions |
| Drift-event reconciliation with N-of-M confirmation + dedup-on-write | `quirk/scanner/hardware_drift.py` `reconcile_device_history` | The precedent pattern for "don't trust a single observation" |

**Implication for scoping (inference, stated as such):** v5.18's hard problem is *not* building a
tracker. It is **giving roadmap items an identity** so that a roadmap item can be joined to the
finding fingerprints that justify it, and then closed by their absence. Everything else in this
document is downstream of that decision.

## 1. How comparable tools close the loop

### 1.1 The universal rule: closure is machine-observed, not human-asserted

Every mature scanner in this space computes finding state from **successive scan observations**, and
exposes a small state machine. It is remarkably consistent:

| Tool | States | Closure semantics | Confidence |
|---|---|---|---|
| Tenable Vulnerability Management | `New` / `Active` / `Fixed` / `Resurfaced` (API: `open` / `reopened`) | "Fixed" = "must have been once present on an asset, but is now no longer found." `Resurfaced` = was present → Fixed → returned | HIGH (vendor docs) |
| Qualys VMDR | `New` / `Active` / `Fixed` / `Re-Opened` | "New" on first detection; "Active" on ≥2 detections; "Fixed" only when *verified by the most recent scan* AND *detected by the previous scan*; "Re-Opened" when a previously-Fixed item returns | HIGH (vendor docs) |
| Dependency-Track | Analysis state (VEX vocabulary) + suppression | Triage decisions persist across re-evaluations; suppression carries over when the same component reappears in a new BOM, with an audit-trail comment recording the history | MEDIUM (docs + issue tracker) |
| Orca Security | Alert lifecycle + bi-directional Jira | When a ticket is marked resolved, Orca **automatically re-scans to verify** and **re-opens the Jira ticket if the issue is still present** | MEDIUM (vendor blog/partner page) |
| Tenable (ticketing) | Bi-directional Jira Cloud / ServiceNow via Exposure Response | Validates effectiveness of response actions via subsequent scan results before tickets close | MEDIUM (vendor solution brief) |

**The design lesson, uniform across all five: the tracker never owns truth about closure. The scanner
does.** A ticket transition is an *intent* signal; the next scan is the *verification* signal. Orca
makes this explicit by re-opening tickets that fail verification.

**Note the Qualys two-sided condition** — Fixed requires *both* "detected by the previous scan" *and*
"verified fixed by the most recent scan", and Qualys explicitly "does not mark QID as closed if
scanner does not recheck same vulnerability." That second clause is the single most important
guardrail in this whole document; see §5.3.

### 1.2 In-tool tracking vs. push-to-tracker: what each costs

Three architectures exist in the wild:

**(A) Push-only (fire and forget).** Create a ticket; never read status back. Dedup by fingerprint so
you don't spam. **This is exactly what QUIRK does today** — `TicketingChannel` implements
`find_by_fingerprint` → `add_rediscovery_comment` or `create_issue`, and the ABC has *no* method for
reading a ticket's status.
*Cost:* the tool can never say "this is being worked on"; the consultant sees only present/absent.
*Benefit:* zero coupling, no credential lifetime beyond the scan, no stale mirror.

**(B) Bi-directional sync (Tenable Exposure Response, Orca).** Read ticket status back; reconcile.
*Cost:* a persistent integration with long-lived credentials, a reconciliation loop that must run
between scans, and a permanent class of "my mirror disagrees with Jira" support burden. It also
requires the tool to be *running continuously*, which is a fundamentally different operating model
from a consultant's episodic engagement.
*Benefit:* in-progress visibility; the ability to re-open a wrongly-closed ticket.

**(C) In-tool state with triage persistence (Dependency-Track).** Own the state entirely; make triage
decisions (suppress, not_affected, resolved) sticky across re-scans, with an audit trail.
*Cost:* you must solve identity yourself (Dependency-Track can, because a component PURL is a strong
identifier — QUIRK's `host:port` is much weaker; see §5.4). Risk-acceptance decisions can silently
outlive their justification.
*Benefit:* no external dependency; works offline; the deliverable is self-contained.

**Recommendation (opinionated, inference from the above):** v5.18 should build **(C) plus a hardened
(A)** — own the state, keep push-only ticketing, and explicitly *defer* status readback (B). Rationale:
QUIRK is episodic consulting software delivered as a CLI + local dashboard + a document. Model (B)
presumes a continuously-running SaaS control plane, which is the parked SaaS block, not v5.18. The
consulting deliverable must be self-contained and reproducible offline; a state model that depends on
a live Jira read is not.

### 1.3 PQC-specific inventory tools

The PQC-native vendors (IBM Guardium Quantum Safe / Guardium Cryptography Manager, SandboxAQ AQtive

analysis, tracking, and remediation insights", "monitor policy violations and track progress",
"visibility, control and remediation" (MEDIUM confidence — vendor marketing and product docs; I could

**Honest gap:** I found no public documentation of a PQC-specific finding *state machine* (the

down against a QUIRK-invented roadmap list, because the target is externally defined.

## 2. What a consultant needs at the second engagement

The billable unit is an assessment, so re-engagement value must be *legible in a document*.

Penetration-testing consulting has already converged on the artifact set (MEDIUM confidence — multiple
consulting-firm sources agree, but all are marketing content, none authoritative):

1. **The retest / delta report** — the vulnerabilities from engagement N, each re-verified, with the
   fix confirmed or rejected. Regression-checked so a fix hasn't introduced new issues.
2. **The attestation / summary letter** — a 1–2 page artifact for third parties (auditors, customers,
   partners). Its consistently-cited field set is a ready-made template:
   - the legal entity tested
   - **what was tested, named as assets** (i.e. explicit scope)
   - the **window dates**
   - the methodology followed
   - the **access level the testers held**
   - findings by severity
   - **current remediation state, with the date closure was verified**
3. **A burndown** showing risk-weighted exposure declining, not merely tickets closing.

One widely-repeated practitioner claim: **"roughly one in six findings that clients believe are closed
will not survive a competent re-test."** (LOW confidence — single vendor blog, no methodology given. Do
not cite this number in QUIRK's own output.) The *directional* point is well-supported though: the
retest exists precisely because client-asserted closure is unreliable, which is the same conclusion §1.1
reaches from the tooling side.

**Program-metric guidance** (MEDIUM confidence, multiple sources): track MTTR **separately by severity**;
"a high overall fix rate driven by easy low-risk findings can mask poor performance on findings that
actually matter"; and the most common failure is treating the SLA as a reporting metric without
**verified closure** — "verified closure confirms fixes are applied rather than tickets acknowledged."

**Scoping implication:** the highest-value v5.18 deliverable is a **re-engagement delta document** whose
content model is the attestation-letter field set above, driven by machine-verified closure. Note that
`docs/` already has a consulting-grade content model (`quirk/reports/content_model.py` feeding
CLI/HTML/PDF/DOCX from v5.2) — the delta report is a new *section* in an existing pipeline, not a new
pipeline. Prefer that over a new dashboard tab as the primary surface; the dashboard is the consultant's
working view, the document is the billable artifact.

## 3. The attestation / evidence problem

### 3.1 There is already a standard for this, and QUIRK already emits its container format

CycloneDX 1.6 — the exact spec QUIRK's CBOM targets — carries a **VEX impact-analysis vocabulary**
verified directly from `schema/bom-1.6.schema.json` (HIGH confidence, read from the schema, not prose):

`impactAnalysisState` enum:
| State | Schema definition (verbatim) |
|---|---|
| `resolved` | "The vulnerability has been remediated." |
| `resolved_with_pedigree` | "The vulnerability has been remediated and evidence of the changes are provided in the affected components pedigree containing verifiable commit history and/or diff(s)." |
| `exploitable` | "The vulnerability may be directly or indirectly exploitable." |
| `in_triage` | "The vulnerability is being investigated." |
| `false_positive` | "The vulnerability is not specific to the component or service and was falsely identified or associated." |
| `not_affected` | "The component or service is not affected by the vulnerability. Justification should be specified for all not_affected cases." |

`impactAnalysisJustification` (required-in-practice for `not_affected`) includes
`protected_at_perimeter` and `protected_by_mitigating_control` — which map cleanly onto QUIRK's
existing `upstream_mitigated` bridge-promotion concept from v5.10.

`impactAnalysisResponse`: `can_not_fix`, `rollback`, `update`, `will_not_fix`, `workaround_available`.

**Verified library support:** the installed `cyclonedx-python-lib` **11.7.0** exposes
`cyclonedx.model.impact_analysis.ImpactAnalysisState` / `...Justification` / `...Response` and
`cyclonedx.model.vulnerability.VulnerabilityAnalysis(state, justification, responses, detail,
first_issued, last_updated)`. `first_issued` / `last_updated` are exactly the "date closure was
verified" fields §2 asks for. **This is buildable today with zero new dependencies.**

**Verified non-support:** CycloneDX 1.6 also defines `declarations` (CDXA — assessors, attestations,
claims, evidence, targets, `affirmation`, JSF `signature`) — the OWASP-blessed mechanism for a signed,
third-party-assessor conformance claim, which is *conceptually a perfect fit* for a consultant
attesting to a client's CNSA 2.0 conformance. **But `cyclonedx-python-lib` 11.7.0 has no
`declarations` model module** (verified: `cyclonedx.model` exposes `bom, bom_ref, component,
component_evidence, contact, crypto, definition, dependency, impact_analysis, issue, license,
lifecycle, release_note, service, tool, vulnerability` — no `declarations`). Emitting CDXA would mean
hand-rolling JSON outside the library's object model and outside its serializer's validation.

**Verified current state:** QUIRK's `quirk/cbom/builder.py` emits **no `vulnerabilities` array at all**
today (grep for `Vulnerability`/`analysis` returns nothing). So VEX would be a genuinely new CBOM
surface, not a modification of an existing one.

### 3.2 What evidence standard does "item 7 is complete" actually need?

Synthesizing §1.1, §2, and §3.1 (this synthesis is my inference; the inputs are cited):

A defensible closure record needs **five** things, and QUIRK can produce all five mechanically:

1. **What was claimed closed** — a stable item identity, not a template title.
2. **Prior positive observation** — the item was *observed present* in a named prior scan session.
   (Qualys's "detected by the previous scan" precondition.)
3. **Current negative observation from an in-scope probe** — the item was *looked for and not found*,
   by a scan whose scope demonstrably covered the asset. Absence-from-the-report is not evidence;
   absence-from-a-successful-probe is.
4. **The verification timestamp and the scan session ID** that produced it.
5. **The reason class** — did the weakness go away (`resolved`), was the asset re-classified
   (`not_affected` + justification), or was the finding wrong (`false_positive`)? These are *not*
   the same claim and an auditor will treat them differently.

**The asymmetry that should govern v5.18's design:** a false "open" costs the client a wasted
remediation cycle. A false "closed" costs the *consultant* their attestation, and — given QUIRK's
existing NIST SP 800-208 / CNSA 2.0 / ISO 27002:2022 mappings and copy-pasteable audit language in the
CBOM compliance guide — potentially propagates into a client's regulatory filing. **Closure must fail
closed.** Any ambiguity (scan error on the host, host not in scope this run, scanner degraded, probe
timed out) must resolve to "not verified", never to "closed".

This is directly analogous to a defect QUIRK already lived through: TRIAGE-176-03, where `ssh-audit`
was invoked with a bad argv, exited 2 with empty stdout, and **every SSH scan silently degraded to a
banner grab** — for the entire life of the integration. Under a naive closure rule, that degradation
would have auto-closed every SSH algorithm finding in the fleet and emitted an attestation saying so.
**The closure rule must require positive scanner-health evidence for the specific probe that would
have re-found the item**, not merely "the scan completed."

## 4. Regulatory timing pressure — and yes, it argues for deadline-relative burndown

The pressure changed materially in mid-2026 and this is the strongest single argument for scoping
v5.18 around **burndown against an external deadline** rather than burndown against a QUIRK-generated
list.

### 4.1 Executive Order 14412 (HIGH confidence — read from the Federal Register full text)

**"Securing the Nation Against Advanced Cryptographic Attacks"**, signed **June 22, 2026**, published
**June 25, 2026** (91 FR, Vol. 91 No. 121, doc. 2026-12909). Explicit deadlines:

| Deadline | Obligation |
|---|---|
| EO + 30 days | Each agency head identifies its PQC migration lead to OMB |
| EO + 90 days | OMB issues guidance requiring agencies to review their HVA / high-impact-system inventory and submit a migration plan |
| EO + 180 days (≈ 2026-12-19) | **CISA/NIST release public guidance describing the minimum elements for a cryptographic bill of materials**; NIST initiates a PQC migration pilot (complete by 2027-12-31); FAR Council publishes a proposed rule requiring covered contractors to comply by 2030-12-31; NIST/FAR Council revise CMVP processes |
| EO + 270 days | NSA reports to the President on PQC migration status; FAR Council proposed rule on contractor vulnerability disclosure |
| **2030-12-31** | Agencies transition **all HVAs and high-impact systems to PQC for key establishment**; covered contractors comply |
| **2031-12-31** | Agencies transition all HVAs and high-impact systems to **PQC for digital signatures** |

**Two consequences for QUIRK specifically.** First, the key-establishment (2030) and digital-signature
(2031) deadlines are **separate**, which means a single scalar "PQC readiness %" is now
*under-specified* against the actual mandate — a burndown must be able to split KEX from signature.
QUIRK's scanners already separate these (SSH kex vs hostkey, TLS group vs cert sig alg), so the data
exists. Second, the **CBOM minimum-elements guidance due around 2026-12-19 is a direct schema-risk
event for QUIRK's core deliverable** and lands inside v5.18's likely lifetime — worth an explicit
watch item, not a build item.

### 4.2 OMB M-26-15 (MEDIUM-HIGH confidence — whitehouse.gov PDF exists at a canonical URL; details
from secondary reporting, PDF not directly parsed)

"Execution of the Migration to Post-Quantum Cryptography", published **June 24, 2026**, two days after
EO 14412. Reported to establish a **five-phase migration schedule spanning 2026–2035**, require agency
migration plans within 120 days, prioritize HVAs / high-impact systems / data expected to remain
sensitive in 2030, name ML-KEM (FIPS 203) / ML-DSA (FIPS 204) / SLH-DSA (FIPS 205), and direct agencies
to **use automation for inventory, policy enforcement, and compliance reporting**. That last clause is
as close to a procurement tailwind for QUIRK as a federal memo gets.

*Caveat:* secondary sources disagree on the EO number, some citing "EO 14409". The Federal Register
document (2026-12909) says **14412**; use 14412.

### 4.3 CNSA 2.0 (MEDIUM confidence — NSA's own PDF returned HTTP 403 to automated fetch; dates below
are from multiple concurring secondary sources and should be re-verified manually before shipping them
into a report)

- **2027-01-01** — procurement gate: new NSS acquisitions must support CNSA 2.0.
- Software/firmware signing: support & prefer by 2025 → **exclusive by 2030**
- Networking equipment (VPNs, routers): support & prefer by 2026 → **exclusive by 2030**
- Web browsers/servers, cloud services: support & prefer by 2025 → **exclusive by 2033**
- Operating systems: support & prefer by 2027 → **exclusive by 2033**
- Niche/constrained equipment, large PKI: support & prefer by 2030 → **exclusive by 2033**
- Custom applications / legacy equipment: update or replace by **2033**

### 4.4 NIST IR 8547 (MEDIUM confidence)

Initial public draft, **2024-11-12**. RSA-2048 / ECC P-256-class (~112-bit) algorithms **deprecated
after 2030**, **disallowed after 2035**. Reported as *still not finalized as of mid-2026* — so it is
guidance, not a binding standard, except insofar as OMB M-26-15 directs alignment with it.

### 4.5 Verdict on the question asked

**Yes — burndown-against-deadline should be a first-class concept, and it is the single highest-value
framing available to v5.18.** Justification:

- The deadlines are **now legally concrete, dated, and asset-class-specific** (§4.1, §4.3), which means
  "days of runway remaining for this asset class" is a *computable, externally-defensible* number rather
  than a QUIRK opinion.
- QUIRK **already has the asset-class taxonomy the deadlines are written in**: networking equipment
  (v5.7–v5.10 hardware fingerprinting + 8-vendor PQC compatibility matrix + CNSA 2.0 tiers), web
  servers/browsers (TLS), OS/software signing (code-signing cert inventory from v5.1), PKI (AD CS,
  Vault PKI). The CNSA 2.0 category table in §4.3 maps almost 1:1 onto QUIRK's existing scanner
  families.
- QUIRK already has **`quirk/scanner/hardware_forecast.py`** — deadline-relative forecasting is an
  established in-repo pattern for hardware EOL, not a novel concept to invent.
- It converts the second engagement's headline from "your score went 62 → 68" (which the client cannot
  act on or defend) into "you closed 14 of 31 items; 6 remain in the class whose CNSA 2.0 exclusive-use
  date is 2030-01-01, ~3.3 years of runway" (which they can put in a board deck).

**Caution:** these dates are *catalog data with a staleness half-life* — EO 14412 and M-26-15 both
landed inside a 3-day window in June 2026 and invalidated the prior consensus. Per this repo's own
staleness discipline (CLAUDE.md's seven `last_verified` catalogs), **any deadline table shipped in
v5.18 must be a versioned catalog with `last_verified` + `source_url` + a CI staleness gate**, not
constants inlined into scoring. A 90-day cadence matching QRAMM/CMVP is the right precedent.

## 5. Failure modes — name the traps

### 5.1 Silent decay of the closure record (the trap this repo has already been burned by, twice)

QUIRK's institutional scar tissue is *records that rot without failing*: the seven `last_verified`
catalogs exist because compliance mappings decayed silently; the UAT zero-undispositioned gate exists
because cases went unrecorded; TRIAGE-176-03 hid inside a test that asserted on `return_value` and
never on `call_args`.

Remediation state is the **highest-decay-risk data QUIRK would ever hold**, because unlike a scan
result it is *not recomputed from scratch each run* — it accumulates. A stale `resolved` is
indistinguishable from a correct one by inspection.

**Mitigations to design in from day one:**
- Every closure record carries the **scan session ID that verified it** and the **verification date**;
  a closure whose verifying session is older than N days is displayed as "closed, unverified since
  <date>", never as plain "closed".
- Prefer **recomputation over storage** wherever possible. `reconcile_device_history`'s D-03 decision
  ("the N-of-M state is recomputed from history on every call") is the right precedent: store
  *observations*, derive *state*.
- **Retention interaction:** `purge_stale_hardware_history` hard-deletes rows older than
  `scan.hardware_history_retention_days`. If closure state is derived from observation history and
  history is purged, **closures silently un-close or become underivable**. Any derived-state design
  must state explicitly what happens when the supporting observations age out — and it must not be
  "the item quietly reappears as open" or "the item quietly stays closed forever."

### 5.2 Regression / resurfacing

Every tool in §1.1 has a distinct `Resurfaced` / `Re-Opened` state, and none of them collapse it into
`New`. **This is not a nicety** — a finding that was fixed and came back is a *process failure* and a
materially different conversation with the client than a newly-discovered one. Orca goes further and
mechanically re-opens the downstream ticket.

**Trap:** if v5.18 models only `open`/`closed`, a regression is indistinguishable from a new finding,
and the burndown chart will show the item closing twice — inflating apparent progress. Model the
resurfaced state explicitly, and make it the *loudest* thing in the delta report.

### 5.3 Scope drift between scans → false mass-closure

**This is the highest-severity trap and the most likely to actually happen to QUIRK**, because QUIRK's
scope is *operator-configured per run* — port scope (v5.6 discovery control), target lists, scan
profile (quick/standard/deep), optional extras (`[hw]`, `[identity]`, `[api]`...), credential presence
(v5.1 ephemeral `CredentialContext`), and sensor-fleet coverage (v5.4/v5.5 distributed). Any of these
narrowing between engagement N and N+1 produces a smaller finding set that *looks exactly like
successful remediation*.

Concretely: a consultant who runs `--profile quick` at the re-engagement, or forgets the `[hw]` extra,
or runs without credentials, would — under a naive "absent ⇒ fixed" rule — generate an attestation
claiming dozens of items closed.

**Qualys's guard is the correct one and should be copied verbatim in spirit:** *do not mark closed if
the scanner did not recheck that specific item.* Closure requires proof the probe ran, targeted that
asset, and succeeded. Practical form:
- Compute and persist a **scope signature** per session (targets, port scope, enabled scanners,
  profile, credential-presence flags, sensor set) and **refuse to compute closure across sessions whose
  scopes are not comparable** — or compute it only over the intersection, and label the rest
  "out of scope this run", never "closed".
- Reuse the existing scan-error infrastructure: `trends.py` already excludes
  `current_error_hosts` — `(host, port, protocol)` tuples with scan errors — from the resolved set.
  **That exclusion is exactly the right instinct and must be extended**, not just inherited: error-free
  is necessary but not sufficient; degraded-but-exit-zero (the TRIAGE-176-03 shape) is the harder case.

### 5.4 Re-scan identity — "is this the same host?"

Vulnerability management's hardest unsolved problem, and QUIRK's identifiers are *weaker* than the
field's norm. VM tools reconcile via agent UUID, MAC, serial number, cloud instance ID, hostname
history, and directory linkage; the literature is explicit that duplicate records "create the
impression that remediation is progressing when the underlying host remains exposed," and that
"if you rebuild a system, you lose the scanner-assigned UUID, which creates another duplicate asset."

QUIRK's match keys today are `(host, port, protocol[, severity])` (trends) and
`SHA256(host:port::title)` (ticketing). Both break on:
- **DHCP / re-IP** — same box, new address → old items falsely close, new items falsely appear.
- **Hostname vs IP** — the same asset scanned as `web01` in one engagement and `10.0.1.5` in the next
  is two assets.
- **Load balancers / VIPs / anycast** — one `host:port` is N backends; one fixed, three not → the
  finding is simultaneously closed and open, and which you see depends on probe luck. This one has no
  clean answer and should be *disclosed*, not silently resolved.
- **Ephemeral cloud/container hosts** — churn produces 100% "closure" plus 100% "new findings" every
  scan.
- **Port remapping** — the service moved from 8443 to 443; the fingerprint says one closed, one new.

**Recommendation (opinionated):** do **not** attempt full entity resolution in v5.18. Instead:
(a) make identity **explicit and inspectable** — the delta report names the join key it used;
(b) provide an operator-supplied **asset alias/stable-ID mechanism** for the engagement (a consultant
scanning the same client twice can supply the mapping — this is a *consulting* tool, the human is in
the loop and is the cheapest reliable resolver);
(c) classify unmatched assets as **"not observed"**, a third state distinct from open and closed, and
surface the count prominently. A delta report that says "9 closed, 4 open, 12 assets not observed this
run" is honest; one that says "21 closed" is a liability.

### 5.5 The PQC-specific closure ambiguity: "partially migrated" is the normal state

Generic VM has a binary (patch applied or not). PQC migration does not:
- **Hybrid KEX** (e.g. `X25519MLKEM768`, already a QUIRK scoring-ceiling target since v5.0) is
  quantum-safe for key establishment but still contains classical material. Is the item closed?
- **Support-and-prefer vs. exclusive-use** — CNSA 2.0's own timeline (§4.3) has *two* dates per
  category precisely because these are different states. An endpoint that *offers* ML-KEM but still
  *accepts* X25519 satisfies the 2025/2026 milestone and fails the 2030 one. **Closure must be
  relative to a named target date, not absolute.**
- **KEX vs. signature** are separately deadlined (2030 vs. 2031 per EO 14412). A host can be closed
  for one and open for the other.
- **`upstream_mitigated`** (v5.10) — a device fronted by a PQC-capable bridge. Maps to VEX
  `not_affected` + `protected_at_perimeter`, which is *not* `resolved`, and an auditor will care about
  the difference.

**Trap:** a single boolean `closed` flag will collapse all four distinctions and produce attestations
that are technically false. The state model needs at minimum `resolved` / `not_affected(+justification)`
/ `partially_resolved-or-target-relative` / `open` / `resurfaced` / `not_observed`.

### 5.6 Roadmap-item churn (QUIRK-specific, arising from §0)

Because roadmap items are regenerated from aggregate counters every run and keyed by generated
`title` string:
- Fixing *one* of eight plaintext endpoints does not close "Remove plaintext HTTP exposure" — the item
  persists with a changed count. **Aggregate items have no closure event, only a magnitude.**
  Burndown-by-item-count on today's model would show zero movement for seven of eight fixes.
- Conversely, the *last* endpoint being fixed makes the item vanish from the generated list entirely —
  disappearance-from-generation is not a closure record, and nothing persists to say it ever existed.
- Any change to a template title string (a wording improvement, a driver-hint tweak) **silently
  re-keys the item**, orphaning its history. This is the same class of bug as the CBOM golden-fixture
  drift already in this repo's memory ("relabel a builder map name → also update classifier
  `_ALGORITHM_TABLE`"). If titles become identity, they need a stability contract and a test.

**Design consequence:** roadmap items must acquire an **explicit stable ID decoupled from the title**,
and must carry the **set of finding fingerprints that constitute them**, so that progress is
"6 of 8 constituent findings verified closed" rather than a binary. That is the actual v5.18 core
data-model change.

---

## 6. Recommended shape for v5.18 (opinionated synthesis)

**Build:**
1. **Item identity + constituent-fingerprint model.** Stable roadmap item IDs, decoupled from title,
   each joined to the finding fingerprints (`SHA256(host:port::title)`) that justify it. This is the
   prerequisite for everything else and should be phase 1.
2. **Observation-derived state machine**, recomputed not stored where possible:
   `open / resurfaced / resolved / not_affected(+justification) / not_observed`. Fail closed.
3. **Scope signature per session** + a hard refusal to compute closure across incomparable scopes.
   This is the anti-false-attestation guardrail and is not optional.
4. **VEX emission in the CBOM** — `vulnerabilities[].analysis` with `state`, `justification`,
   `detail`, `first_issued`, `last_updated`, using `cyclonedx-python-lib` 11.7.0's existing
   `VulnerabilityAnalysis`. Zero new dependencies; makes closure claims machine-readable and
   standards-anchored rather than QUIRK-proprietary.
5. **Deadline catalog** (EO 14412 / M-26-15 / CNSA 2.0 / IR 8547) as a `last_verified` +
   `source_url` + CI-staleness-gated module, on the QRAMM 90-day cadence. Split KEX vs signature.
6. **Re-engagement delta report section** in the existing `content_model.py` pipeline, structured on
   the attestation-letter field set from §2 — entity, named in-scope assets, window dates,
   methodology, access level, findings by severity, remediation state with verification date.

**Explicitly defer:**
- **Bi-directional ticket status readback** (model B). Wrong operating model for episodic consulting;
  belongs with the parked SaaS block.
- **Automated entity resolution / asset fuzzy-matching.** Use operator-supplied aliases + an honest
  `not_observed` bucket instead.
- **CDXA `declarations` / signed attestations.** Conceptually the right long-term home for a
  consultant's conformance claim, but `cyclonedx-python-lib` 11.7.0 has no model for it; hand-rolling
  signed JSF outside the library is a milestone of its own.

**Watch (not build):** the CISA/NIST **CBOM minimum-elements guidance due ≈2026-12-19** per EO 14412
§180-day tasking. It may constrain QUIRK's flagship artifact and lands within v5.18's window.
