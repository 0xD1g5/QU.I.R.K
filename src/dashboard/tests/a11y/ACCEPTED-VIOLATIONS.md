The 2026-08-27 baseline froze `count: 1` from one particular CI render; the 2026-09-02 GitHub-hosted `Dashboard Quality` run (first-ever execution of this a11y suite against this `main` history — v5.16/v5.17 were developed but never pushed until this phase) observed `count: 2` with zero intervening changes to this page, `components/ui/table.tsx`, or any `tests/a11y/` fixture since the baseline was authored (`git log --since=2026-08-27` on all three is empty). This is a baseline-fragility finding, not a regression — tracked as a follow-up to replace the exact-count pin with a tolerance/range, or to fix `table.tsx` directly so the rule zeroes app-wide.

Tolerance addendum (Phase 216, HARNESS-03, D-10/D-13/D-14): the exact-count pin's own follow-up (above) is resolved here with a MEASURED, transitional range rather than a wider exact pin or a global tolerance. Two observed counts feed the range: macOS local run (`npm run a11y:check` / `npm run a11y:check:light`) observed `scrollable-region-focusable` count 1 for /data-at-rest in BOTH themes; the pinned Linux CI runner (workflow_dispatch run 36613039581, Chrome 152.0.7977.82) observed count 2 in BOTH themes. `countRange: [1, 2]` is set on this entry in both `baseline-data-at-rest-default-dark.json` and `baseline-data-at-rest-default-light.json`, covering both measured platforms; `count` stays pinned at the Linux-observed 2 so nothing else's semantics change. A GLOBAL tolerance band (applied to every entry, not just this one) was rejected per D-10: a loose band could hide a real regression on any other route/rule, whereas this range is scoped to the one entry that is measurably render-dependent. The stale-entry ratchet still fires against this range's lower bound per D-12 — a future run reporting 0 still fails, only 1 and 2 are tolerated. This range is TRANSITIONAL, not permanent: KBD-01 (Phase 219, REQUIREMENTS.md) adds `tabIndex`/`role` to `src/dashboard/src/components/ui/table.tsx` and WITHDRAWS the `scrollable-region-focusable` acceptance outright — once that lands the rule should zero out app-wide and this range must be RETIRED, not renewed by inertia. Empty/loading fixture variants for this route are deliberately NOT ranged: macOS observed 0, Linux observed 2, a spread `[1,2]` cannot cover, and a `[0,2]` band would set the ratchet floor to zero — the exact loose-tolerance failure mode D-10 rejects.
